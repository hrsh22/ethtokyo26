# World prize update - Tokyo 2026

Current implementation work and prize targets are specified in the [verified-person → named-agent delegation plan](ens-world-integration-plan.md). The review below records the earlier assessment; its registration and screening prerequisites have since changed.

Checked 25 September 2026 against the [ETHGlobal prize page](https://ethglobal.com/events/tokyo2026/prizes#world), [World ID for Agents sandbox docs](https://sandbox.auth.world.org/docs), the sandbox [OIDC discovery document](https://sandbox.auth.world.org/.well-known/openid-configuration), and World's [official sandbox plugin](https://github.com/worldcoin/world-id-agent-plugin).

## What changed

World now has two distinct $5,000 open tracks. **Best Use of IDKit** still rewards a well-chosen credential at a meaningful human trust moment. Its current brief explicitly asks for the minimum-sufficient credential rationale, a working server/onchain verification, a successful path plus a meaningful failed/cancelled/ineligible path, and an integration debrief. **Best Use of World ID for Agents** requires the official event dev environment and a complete request → human completion → secure backend validation → protected agent action, plus a denied/expired/cancelled path and debrief. The prize page says proofs in the event environment use fake identities; they are not production assurances. The separate Continuity awards have their own participation restriction. [Prize page](https://ethglobal.com/events/tokyo2026/prizes#world)

Accord's person claim is already a strong IDKit story: a beneficiary wallet requests a claim, a fresh Selfie Check session proof is bound to that claim's permit digest, and the backend verifies before signing. The chosen credential is proportionate to **presence and continuity of the enrolled claimant**, not legal identity or a one-person-one-account promise. World's documentation calls Selfie Check medium assurance and says its new `sybil_score` is a risk signal, not a uniqueness verdict. No Sybil threshold is needed for the current claim rule. A real completed World App proof remains pending; the local fixture is useful for testing but cannot be described as a live verification. [Selfie Check](https://docs.world.org/world-id/credentials/11), [IDKit integration](https://docs.world.org/world-id/idkit/integrate), [Accord feedback](integration-feedback.md)

## World ID for Agents: a worthwhile addition with one clear role

Add an **owner approval for an exceptional agent payment**, such as a report purchase above an owner-set threshold or a payment to a newly approved recipient. The agent proposes the exact Space, allocation, token, amount, recipient, and request key; the owner sees those details and approves once. Accord then checks the live ENSv2 mandate and Intercepta verdict and signs its existing short-lived payment permit. A rejection, timeout, mismatched owner, changed intent, or failed risk check issues no permit. This makes World the human control for a real agent decision, while ENS remains agent authority and Intercepta remains recipient screening. Routine payments can stay autonomous under the mandate. This is a recommended product design, not a capability already implemented.

The event's official sandbox is a **separate OIDC federation**, not Accord's existing IDKit RP/session flow. The sandbox docs describe an authorization-code OIDC integration with a pairwise `(iss, sub)` identifier, optional fresh authentication for important actions, and a confidential backend that issues its own app/API authorization after validation. Its discovery metadata publishes the issuer, authorization and token endpoints, JWKS URI, supported `code` response, `openid` scope, `RS256` ID tokens, `auth_time`, `nonce`, `prompt=login`, and PKCE S256. Register a separate sandbox OIDC client and exact **HTTPS** callback in the [portal](https://sandbox.auth.world.org/portal); HTTP localhost callbacks are rejected. The official plugin's developer skill says developer registration uses Google portal sign-in and `developer-portal:manage`, without needing a personal sandbox World ID app; registration needs portal approval and any generated client secret must stay in backend configuration. [Sandbox docs](https://sandbox.auth.world.org/docs), [discovery](https://sandbox.auth.world.org/.well-known/openid-configuration), [plugin README](https://github.com/worldcoin/world-id-agent-plugin), [developer skill](https://github.com/worldcoin/world-id-agent-plugin/blob/main/plugins/world-id-sandbox/skills/world-id-developer/SKILL.md)

Suggested backend flow: persist an expiring, one-use payment intent and expected owner identity; send the owner to an Accord review page; start OIDC with server-held `state`/`nonce` and a fresh-authentication request; exchange the code on the backend; validate ID-token signature via the sandbox JWKS, issuer, audience, expiry, nonce, and authentication time; require the pairwise subject bound to that Space owner; collect an explicit **Approve payment** action for the unchanged intent; atomically consume approval when issuing the existing permit. Exercise success and denied/expired/cancelled paths against the official dev environment. Keep the sandbox issuer, client ID, secret, callback and fake identity data isolated from Accord's production World ID settings. [Sandbox docs](https://sandbox.auth.world.org/docs), [discovery](https://sandbox.auth.world.org/.well-known/openid-configuration), [prize requirements](https://ethglobal.com/events/tokyo2026/prizes#world)

**Important limit:** OIDC authentication proves who completed the sandbox sign-in; it does **not by itself prove that World displayed or cryptographically approved the exact payment amount and recipient**. Accord can correlate an OIDC result with its own one-use intent and explicit review click, but must describe this as *Accord's human approval after World authentication*. The public sandbox docs and OIDC metadata do not establish a World-native exact-payment approval claim. Verify any stronger action-binding feature through the sandbox's `get_idp_guide` before claiming it. [Sandbox docs](https://sandbox.auth.world.org/docs), [discovery](https://sandbox.auth.world.org/.well-known/openid-configuration)

## Scope decision

This is a medium-sized integration because it needs OIDC client registration/HTTPS callback, backend token validation and intent state, owner UI, and both success/failure testing. It should be additive to the existing person claim and ENS/Intercepta payment route. If live setup time is tight, prioritize a single high-value **agent payment awaiting owner approval** journey over a generic World login or broad policy editor. The official [World ID agent plugin](https://github.com/worldcoin/world-id-agent-plugin) is mainly a sandbox MCP sign-in/developer-portal helper; installing it alone is not the app integration required by the prize.

The concrete implementation and demo sequence is in [Owner approval for agent payments](world-agents-approval-plan.md).
